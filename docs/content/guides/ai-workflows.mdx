What we'll build:

- An `aiJob` workflow per job that turns a meeting transcript into a short brief for your sales team.
- Two model steps, extract and summarize, that retry with backoff when the provider is rate limited or down.
- Enrich steps that look up each company in your CRM between the two model calls.
- A publish step that posts the brief to your CMS exactly once.
- A `/jobs` route that starts a job and returns its id right away, and progress events that tell your app which step a job is on.

<Steps>

<Step title="Install">

```sh
npm add @rivet-dev/workflows rivetkit@next hono @hono/node-server
```

</Step>

<Step title="Configure">

Set your model key and the base URLs of your CRM and CMS APIs:

```sh
OPENAI_API_KEY=sk-...
CRM_API_URL=https://crm.internal.example.com
CMS_API_URL=https://cms.internal.example.com
```

`OPENAI_BASE_URL` and `OPENAI_MODEL` are optional. Point `OPENAI_BASE_URL` at any server that speaks the OpenAI chat completions format.

</Step>

<Step title="Call the model">

Every model call goes through one function:

<CodeSnippet file="examples/docs/guides/ai-workflows/model.ts" title="model.ts" />

- Keeping the call in one file means the workflow never depends on a provider. To use Anthropic, Gemini, or an SDK, change only this function.
- A `429` or `5xx` throws a plain `Error`. The workflow step that called it retries with backoff.
- Any other error throws `CriticalError`, which stops retries right away. A bad API key or a malformed request fails the same way every time, so retrying only wastes time.

</Step>

<Step title="Create the workflow">

Each job is its own `aiJob` workflow, keyed by the job id. It waits for a `start` message, then runs the extract step:

<CodeSnippet file="examples/docs/guides/ai-workflows/ai-job.ts" title="ai-job.ts" highlight="retries,extract" />

- `ctx.step` records the step's return value. After a crash or a deploy, the workflow replays and gets the recorded value back instead of calling the model again, so you never pay twice for the same answer.
- `MODEL_STEP` gives model calls up to 7 attempts. The first retry waits 4 seconds and the wait doubles up to 60 seconds, which is enough for most rate limits to clear. The workflow sleeps durably between attempts, so a long wait does not hold a process.
- Model calls can be slow, so the step timeout is 2 minutes instead of the default 30 seconds. `retryOnTimeout` makes a timeout retry like any other error.
- If the model replies with invalid JSON, `JSON.parse` throws and the step asks again.

</Step>

- The loop is safe to replay because the list of companies comes from the recorded extract step, so every replay sees the same list in the same order.

</Step>

<Step title="Summarize with the model">

The summarize step sends the transcript, the action items, and the CRM data back to the model:

<CodeSnippet file="examples/docs/guides/ai-workflows/ai-job.ts" title="ai-job.ts" region="summarize" />

- It uses the same `MODEL_STEP` retry settings as the extract step.
- `companies` and `extracted` are recorded results from earlier steps, so this step can run in a later process than the ones that produced them.

</Step>

<Step title="Publish the result">

The last step posts the brief to your CMS:

<CodeSnippet file="examples/docs/guides/ai-workflows/ai-job.ts" title="ai-job.ts" region="publish" />

- A step can run more than once. If the process dies after your CMS saved the post but before the step was recorded, the step runs again.
- `publishPost` sends the job id as an `idempotency-key` header, so your CMS can return the existing post instead of creating a second one. See `tools.ts` in the previous step.

</Step>

<Step title="Report progress">

Every step calls `setStage`, and the `onError` hook reports retries:

<CodeGroup>
<CodeSnippet file="examples/docs/guides/ai-workflows/ai-job.ts" title="setStage" region="progress" />
<CodeSnippet file="examples/docs/guides/ai-workflows/ai-job.ts" title="onError" region="on-error" />
</CodeGroup>

- The stage lives in `state`, so a client that connects late can call `getStatus` and see where the job is.
- `broadcast` pushes each change to every client connected to the job. No separate pub/sub service is needed.
- `onError` sees each failed attempt with its retry delay. It only observes, so it is a good place for progress updates and error reporting, but not for work the job depends on.

</Step>

<Step title="Start jobs over HTTP">

The HTTP server has one route. It creates a workflow for the job and hands it the input:

<CodeSnippet file="examples/docs/guides/ai-workflows/server.ts" title="server.ts" highlight="jobs" />

- `send` puts the input on the job's `start` queue and returns as soon as it is stored, so the route answers in milliseconds even though the job takes much longer.
- A new random id per request means each POST starts its own job. To make retries of the same request safe, derive the id from something stable, such as a document id, and `getOrCreate` returns the existing job.

</Step>

<Step title="Try it">

Start the server:

```sh
npx tsx server.ts
```

Then submit a job and follow its progress:

<CodeSnippet file="examples/docs/guides/ai-workflows/client.ts" title="client.ts" />

```sh
npx tsx client.ts
```

The client prints each stage as it happens, including any retries, and then the job's final state.

<Note>
Stop the server while a job is running and start it again. The job continues from the step it was on, and steps that already finished do not call the model or your APIs again.
</Note>

</Step>

</Steps>
